PCD ROADMAP
===========

Current release: 0.2.5. Next release: 0.2.6.
Work through planned releases in the order below. Within each release, follow the listed order.
Versions after 0.2.6 are planning targets, not fixed delivery dates.
Release when its acceptance checks pass; do not delay it for tasks assigned to later versions.


0.2.6 - PERFORMANCE AND CLI OUTPUT
----------------------------------

Search/picker scope for 0.2.6: reuse the history snapshot and initial ordering
within one CLI operation. Full resolution and storage work belongs to 0.3.0.
The numbered list contains only remaining work.

    1. Extend the existing cache, search, memory, and scan benchmarks and record baselines
       before changing algorithms.
       Cover CLI startup, exact/fuzzy navigation, completion, shell wrappers, and history I/O.
       Include cache misses, empty caches, add operations, and large/wide directory trees.
       Measure broad and selective queries at multiple catalog sizes.
       Measure time separately from memory; report distributions, not only best runs.
    2. Avoid scanning all roots twice during `pcd add`.
       Preserve conflict detection and config/cache correctness.
    3. Expand shell E2E coverage beyond the behavior changed in 0.2.4 and 0.2.5.
    4. Compare end-to-end latency and memory with the baseline.
       Retain optimizations only when they improve measured behavior without regressions.
    5. Add a compact Added / Removed / Total summary to `pcd refresh` and test it.
       Add an optional detailed mode that prints added and removed paths.
    6. When `pcd <project>` misses an exact name in the cache, discover newly added
       repositories and navigate to an exact match without requiring `pcd refresh`.
       Avoid scanning on exact cache hits; measure the cost of repeated misses.


0.2.7 - DATA RELIABILITY
------------------------

    1. Test concurrent configuration mutations and cache publication together.
       Preserve existing config read-modify-write locking.
    2. Prevent an older refresh from overwriting a newer cache snapshot.
    3. Define handling of partial scans caused by filesystem errors.
       Do not publish a partial result as an ordinary complete cache snapshot.
    4. Store discovery provenance and correct root project counts (deferred from 0.2.3).
       The current cache retains one display path per canonical project, losing other routes.
       Count a project once in every root through which it is discovered, not merely contained.
       Version the cache schema and rebuild older snapshots without changing user configuration.
       Add regression tests for shared symlink targets, followed symlink trees, overlapping roots,
       and nested roots separated by exclusions or repository boundaries, including cache reloads.
    5. Synchronize parent directories after atomic replacement for crash durability.
       Verify supported platforms and measure the extra write cost.


0.3.0 - PROJECT STORAGE AND RESOLUTION
--------------------------------------

    Design and validate the storage migration independently of aliases.
    Complete the resolve contract: one storage-agnostic lookup, refresh/retry in the
    resolver, and a picker that displays a bounded result set and re-resolves edited
    queries. Preserve exact duplicates, fuzzy ranking, manual registrations, and
    cache-only completion. Remove the fuzzy fallback's second JSONL pass without
    regressing exact lookup. Compare startup, refresh, time, disk, and memory on all
    supported platforms before replacing JSONL; do not mix migration with aliases.


0.3.1 - PROJECT INSPECTION AND EXCLUSIONS
----------------------------------------

    1. Add `pcd info <project>` with metadata and status.
       Add appropriate project completion with the command.
    2. Extend `pcd remove <project>` to manual and discovered projects without deleting directories.
       Unregister manual projects and persist discovered project paths as exclusions.
       Let `pcd add <path>` restore excluded projects and complete all removable projects.
    3. Add `pcd doctor`.
       Check configuration, cache, roots, missing projects, PATH, and detectable shell integration.
    4. Document and test refresh behavior with exclusions and unavailable projects.
       Preserve user configuration and report stale references rather than deleting them silently.


0.4.0 - PROJECT ALIASES
-----------------------

COMMANDS
    pcd alias add <project> --as <alias>
    pcd alias remove <alias>
    pcd alias list

REQUIREMENTS
    Reference concrete project paths and survive `pcd refresh`.
    Detect conflicts with commands, projects, and other aliases.
    Show aliases in `pcd list` and `pcd info`.
    Report stale aliases in `pcd doctor`.
    Complete aliases in relevant commands.


0.5.0 - PROJECT GROUPS
----------------------

COMMANDS
    pcd group create <group>
    pcd group add <group> <project> [--as <member-name>]
    pcd group remove <group> <member-name>
    pcd group delete <group>
    pcd group list
    pcd group show <group>

NAVIGATION
    pcd <group>
    pcd <group>/<member-name>

REQUIREMENTS
    Use local member names and reference concrete project paths.
    Do not depend on parent directory names; survive `pcd refresh`.
    Allow the same member name in different groups.
    Resolve conflicts with commands, projects, and aliases deterministically.
    Keep `--project` available for explicit disambiguation.
    Complete group names and members; show groups in `pcd list` and `pcd info`.
    Report missing group members in `pcd doctor`.
    Preserve manual projects, aliases, and groups while rebuilding discovered projects.
    Remove missing discovered projects from the rebuilt cache, not user-defined references.


0.6.0 - OUTPUT AND SEARCH UX
----------------------------

    1. Align tables using terminal display width for wide Unicode characters.
    2. Evaluate compact JSON and an explicit pretty-print option without silently breaking output.
    3. Add machine-readable output where useful and additional list sorting modes.
    4. Evaluate optional helpers for creating groups from matching project names.
    5. Review frecency ranking using the existing usage count and last-used timestamp.
       History collection and bounded retention already exist; do not reimplement them.
       Keep history lightweight and preserve deterministic unique exact-name resolution.


0.7.0 - ADDITIONAL SHELL SUPPORT
-------------------------------

    Add Nushell support with real shell tests and documentation.
    Keep automatic installation optional and manual configuration supported.


AFTER 0.7.0 - RESEARCH AND OPTIONAL INTEGRATIONS
-----------------------------------------------

Assign a release version to each implementation after feasibility and scope are established.
These are retained ideas, not prerequisites for the releases above.

STORAGE RESEARCH
    Investigate scalable lookup beyond JSONL using the performance benchmark results.
    Compare SQLite with indexed-file alternatives before choosing a format.
    Plan migration, recovery, and compatibility before scheduling a storage change.
    Revisit earlier only if measurements show a practical blocker.

OPTIONAL INTEGRATIONS
    Add tmux integration.
    Add IDE and editor plugins.
    Add direnv integration.
    Add import and interoperability with zoxide.
    Add desktop launcher integration.


CHECKS FOR EVERY RELEASE
------------------------

    Test each behavior change and update help/documentation in the same release.
    Run format, lint, type checks, unit/integration/E2E tests, build, and wheel smoke checks.
    Run relevant real-shell tests and performance comparisons for affected behavior.
    Verify the exact published commit and matching package/tag versions.
    Maintain CI release automation and PyPI publishing; improve shared workflows independently.
    Record migrations and compatibility breaks explicitly in release notes.
